Signature Console 2.0

One desk that answers the only question that matters each hour: which classes deserve capital right now, at what size, at what expected capture — and is live executing them at forecast-grade drag?

1 · Why now

The console (v1) pairs each genome's rule with its result — geometry beside EV — and that scaffolding is right. But the ecosystem has outgrown it. In the last 48 hours the platform gained a wallet-reputation edge (79% win compound cohort), an 11-gate live admission stack, a regime window, fire-sale execution, a chain-proven ledger, and a 30-day forecast with daily scoring. None of that is on the console. Today the operator reconstructs "why isn't class X trading live?" from four surfaces and an audit table. The console must become the place where the whole ecosystem converges into actionable, per-class KPIs — and where the optimized wallet is visible as a recommendation, not a feeling.

3 · The KPI contract (per-class row)

Every class row carries five KPI groups. Each cell is clickable → the class drawer (last 10 trades + last 10 refusals with reasons, mini-replay).

GroupKPIsActionable because
REGIME8h EV%, n, status (ACTIVE / BENCHED / PRIOR), re-admit distancesays whether live is allowed to touch the class and what would change that
SIGNALconfirms/day, smart-money share (wh≥2 & net≥1), avg inflow, golden-window densitysays how much qualifying flow exists and how rich it runs
ADMISSIONfunnel: confirmed → refused (top gate named) → live-filled; refusal-book P&Lseparates "nothing qualified" from "we missed" — and prices what the gates cost
EXECUTIONcapture % (pooled, vs 40%), drag pp (twin gap), unsellable count, TP-banked ratedrag is the number the forecast lives or dies on; capture is the exit report card
MONEYEV/$ (paper · live), P&L, deployed, current vs recommended weightthe allocation column IS the optimized wallet

KPI definitions (frozen)

capture   = Σ dollars kept ÷ Σ dollars peaks offered   -- POOLED, never averaged; rung-gated; per class
drag      = mean( paper_twin_ret − live_ret )          -- same-mint twins, opened ≤120s apart, pp/trade
ev_per_$  = Σ pnl ÷ Σ size + 1                          -- the learning loop's unit, unchanged from v1
sm_share  = confirms(wh≥2 ∧ net≥1 ∧ ★≥1) ÷ confirms    -- point-in-time wallet reads only
refusal_pnl = Σ hypothetical(size_floor × candidate outcome) over refused confirms -- gate cost, labeled HYPOTHETICAL

4 · The Allocation Advisor — the "optimized wallet" output

A deterministic, explainable formula — not a black box. For each class with regime status ACTIVE:

edge_c   = max(0, ev8h_c − drag_c)            -- net edge after measured execution cost
score_c  = edge_c × capture_c × √n_c          -- capture-weighted, evidence-damped
weight_c = score_c ÷ Σ score  (clamped: none > 40% exposure cap, floor $4/position)
BENCHED and PRIOR classes → weight 0, shown with the reason

The console renders current deployed weight vs recommended weight as paired bars per class. Phase 3 adds one-click Apply: writes per-class size multipliers into runtime_overrides.manual with a full audit row — the operator approves every allocation change; nothing self-applies.

Guardrails carried from hard lessons: ratio KPIs pool, never average (capture −347% incident). SIM and ◆ LIVE never sum. Refusal-book P&L is labeled HYPOTHETICAL everywhere it renders. Stale manual pins killed us once (arm 1.03 ghost) — every advisor Apply stamps appliedAt + source and the console shows active pins with age, so no pin is ever invisible again.

5 · Architecture

  • Data layer (queries.ts): getSignatureConsole(v2) assembles one row per class from: positions (EV, capture inputs via fills), candidate_outcomes (signal + wallet KPIs, refusal book), audit_log (admission funnel by reason prefix), twin-join (drag), classRegimeHealth parity query (regime), config.smart_money_forecast (band header). Heavy aggregates go into two SQL views (sig_console_flow, sig_console_twins) so the page render stays <300ms.
  • UI (SignatureConsole.tsx): keep the geometry spine; add the five KPI groups as compact cells with semantic chips (ACTIVE/BENCHED, ⚠ drag>9pp, 🐋 sm-share>15%); class drawer via the house Panel/Drawer standard; header carries the 📐 forecast band + wallet lane filter compliance (?lane=).
  • Advisor engine (packages/core): pure function recommendAllocation(rows, caps) — unit-testable, no DB. Sentinel reuses it nightly to write an allocation_advice config snapshot; console diffs advice-vs-actual next morning.
  • No new daemons, no schema migrations — two views + one config key. Everything derives from tables that already exist.

6 · Phases

Phase 1 — Data layer. Views + getSignatureConsole v2 returning the full KPI contract. Twin-drag calculator with the ≤120s pairing rule. Acceptance: every KPI reproducible by hand-query; drag matches the forecast study's 12.8pp on the same window.
Phase 2 — Console UI. Row redesign + drawers + funnel cells, Panel standard, lane-filter compliant. Acceptance: RENDERED review (not typecheck) on both themes; the Li-class miss (regime skip on a 5.25× smart-money runner) must be reconstructable from the console alone in under 30 seconds.
Phase 3 — Allocation Advisor. Recommended-weight column + Apply flow writing audited pins. Acceptance: advisor output is stable across refreshes on unchanged data; Apply → visible pin with age badge; a second Apply supersedes cleanly.
Phase 4 — Closed loop. Nightly advisor snapshot from the sentinel (Analyzer 2.0 M2 home); console shows last-night's advice vs today's realized per-class P&L — the advisor is itself scored, exactly like the forecast. Acceptance: 7 consecutive nightly snapshots with advice-vs-actual deltas rendered.

7 · Falsifiers & review cadence

  • If advisor-recommended weights underperform equal-weight over 14 days of snapshots, the score formula is wrong — revert to display-only and re-derive.
  • If drag per class disagrees >3pp with the weekly forecast re-measure, the twin-pairing rule is biased — audit the ≤120s join.
  • Console KPIs are frozen definitions (§3); changes require a spec revision (SPEC-002), never a silent redefinition.
