The Ledger System: one journal, every report derived

GR-HERMES-LEDGER-SPEC-001 · 2026-07-22 · status: for review · author: Hermes engineering

1Problem — three ledgers, four shadows, no single truth

Today the "ledger" is three partial surfaces plus four shadow sources, each computing money its own way:

SurfaceScopeWhat it misses
Accounting Ledgerpaper closed positions, running total, recon, forecastlive lane entirely; fees; partial fills
Trade Ledgerround trips, both lanes, tx hashes, SIM marksfees; adjustments; write-offs as first-class entries
Fills Tableraw fill eventsposition context; cost basis; no balance semantics
Shadows: pnl_snapshots (equity curves) · audit_log (events, JSON) · the on-chain wallet (the only real truth for live) · the Trade Performance Analyzer (management scoring)

Every accounting defect found on 07-21 traced to this fragmentation — and each cost real money or real trust:

  • Phantom labels. A trail exit was overwritten to live_desync_empty by a concurrent sweep. P&L right, story wrong — and the Analyzer scores by story.
  • Wallet–ledger drift. The live wallet's on-chain balance and the ledger's sum disagree by an unreconciled residue of fees, dust, and write-offs. Nothing continuously proves they match.
  • Double-books. Duplicate daemons opened the same signal twice; the books recorded both as legitimate. The fix was process-level; the ledger itself would have accepted infinite copies.
  • Invisible fees. Network fees, priority fees, and DEX fees are scattered across fee_usd columns and audit JSON. Nobody can answer "what did execution cost this week?"
The root defect: money facts are stored as mutable rows (a position's exit_reason, realized_pnl_usd) that any code path can overwrite, instead of as immutable events that can only be appended and corrected.

2Design — an event-sourced, double-entry journal

One append-only journal. Every dollar movement is an event carrying balanced double-entry legs. Every report — positions, P&L, equity, fees, statements — is a derived projection that can be rebuilt from the journal at any time. Nothing downstream is ever hand-edited.

Paper and live are separate books sharing this chart. A book is a hard partition — no query may sum across books without an explicit label, which makes the lane-separation rule a schema property instead of a code-review checklist. Every derived statement carries its book's provenance permanently: SIM or LIVE, non-removable.

2.2 The journal

CREATE TABLE ledger_events (
  id            bigserial PRIMARY KEY,
  book          text NOT NULL,              -- 'paper' | 'live'
  event_type    text NOT NULL,              -- see §2.3
  occurred_at   timestamptz NOT NULL,
  -- IDEMPOTENCY: the natural key of the real-world fact. A tx signature,
  -- a fill id, a decision id. UNIQUE — the double-book class dies here.
  idempotency_key text NOT NULL UNIQUE,
  position_ref  bigint,                     -- optional link to the trade
  tx_signature  text,                       -- on-chain evidence (live)
  memo          text NOT NULL,              -- human story, e.g. 'TP0 banked 20%'
  evidence      jsonb NOT NULL DEFAULT '{}'
);

CREATE TABLE ledger_legs (
  event_id  bigint NOT NULL REFERENCES ledger_events(id),
  account   text   NOT NULL,
  -- signed; every event's legs MUST sum to zero (enforced by trigger)
  amount_usd numeric NOT NULL,
  amount_native numeric,                    -- SOL lamports / token qty
  mint      text
);
  • Append-only. No UPDATE, no DELETE — a Postgres rule revokes both. A mistake is corrected by a reversal event that references the original. The desync-overwrite class becomes structurally impossible.
  • Balanced. A trigger rejects any event whose legs don't sum to zero. A buy is cash:sol −$2.00 / inventory +$1.99 / fee:network +$0.01 — by construction, money never appears or vanishes.
  • Idempotent. The unique key means replaying a webhook, retrying a handler, or running two daemons produces one entry. The BSTRAT double-buy would have been one journal event and one loud constraint violation.

Marks are not money. Unrealized P&L, peaks, and floats never enter the journal — they live in projections computed against it. The ledger records what happened; the dashboard estimates what might.

3Reconciliation — the chain is the auditor

For the live book, the blockchain is the only truth. A reconciler job (every 5 minutes) proves the journal against it:

  • Read the wallet's SOL balance and every token account on-chain.
  • Compute the journal's expected balances from account sums.
  • Drift under $0.05 → green heartbeat on the dashboard.
  • Drift over threshold → a recon.adjust event with the measured delta and a mandatory reason, plus a phone alert. Drift is never silently absorbed and never silently ignored.
Definition of done for any trading-code change: the reconciler stays green for 24 hours after it ships. Wallet-vs-ledger divergence stops being a discovery and becomes an alarm.

The paper book reconciles trivially (bankroll + realized = equity) but runs through the same machinery, so a simulation bug surfaces the same way an accounting bug does.

4The reporting layer — statements, not tables

Every report is a projection over the journal. Because the journal is complete and balanced, each one is exact, reproducible, and traceable to evidence rows:

Daily P&L statement
Per book: gross realized, fees by type, write-offs, net — with per-signature and per-venue cuts. The number the PULSE and SUMMARY reports quote, so the phone and the books can never disagree.
Equity statement
Opening balance → trading result → fees → transfers → closing balance, per book per day. Ties to the chain via the reconciler's green check.
Execution cost report
The invisible made visible: network + priority + DEX fees, slippage vs decision mark per venue. Answers "what does a $2 position really cost?" with data instead of the 14%-fee-drag estimate.
Trade dossier
One trip end-to-end: every journal event, every tx hash, the Analyzer's management grade, the signature evidence. The drill-down for any number on any statement.
Tax-lot export
FIFO lots with acquisition/disposal timestamps and proceeds — CSV. Exists from day one so year-end is a download, not a project.
Period statement (investor-grade)
Monthly: performance, fees, drawdown, reconciliation attestation. LIVE and SIM books rendered separately, provenance labels baked into the layout — simulated results can never be dressed as real capital.

5Dashboard — one Ledger workspace

The three current panels collapse into one Ledger workspace on the house Panel standard (core + drawer, KPI tiles, charts — exec-shareable):

  • Header: per-book equity, day's net, fee total, and the reconciler heartbeat (green tick with minutes-since-proof).
  • Statement view (default): the daily P&L statement with expandable per-signature / per-venue rows.
  • Journal view: the raw event stream, filterable, each row opening its trade dossier. ◆ LIVE / SIM marks on every row.
  • Drift view: reconciliation history — every adjustment ever made, with reasons. An empty page is the goal state.

7Invariants — the tests that keep it honest

  • Σ legs = 0 for every event (trigger-enforced)
  • cash:sol never negative in either book
  • Live drift ≤ $0.05 or an alert exists (reconciler)
  • Every writeoff.* carries failure evidence; every recon.adjust carries a reason
  • Idempotency-key collisions are logged loudly — each one is a bug caught before it became money
  • Projections rebuilt from scratch match incremental state (nightly job)
Scope guard. This spec deliberately excludes: multi-wallet support (schema-ready via book, not built), cross-chain, and real-time streaming projections. Each is an additive phase later, not a reason to delay phase 1.
